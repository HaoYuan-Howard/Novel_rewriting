## 1. 结论

当前后端工作流已经能够把真实小说从 Stage 0 跑到 Stage 7，并产出可装配的最终正文。三本样本全部满足：

- Stage 0–4 正式制品齐全；
- Stage 5 全书验收无 HARD；
- Stage 6 文案已人工批准；
- Stage 7 改名映射已人工批准并完成装配；
- 最终章数与计划一致，落盘正文 SHA-1 与账本一致；
- 改名占位符往返恒等检查通过；
- Stage 7 高置信旧名残留为 0。

因此，“后端真实链路能否工作”的答案是 **能**。但现在仍是“可人工监管运行”，不是“可完全无人值守运行”：Stage 6/7 本来就有人工闸门；此外，材料锚点、语义泄密、名字语感等检查仍有明显盲区，AMBER 不能被解释成质量全绿。

## 4. 验证中修复的缺陷

### 4.1 LLM 调用与 Stage 2

- 补齐 Stage 2 全局抽取和逐章蓝图的真实付费生成路径，不再依赖预置制品。
- 改为一章一请求、失败按章隔离，并支持定向章节补跑；长书中个别连接失败不再推倒整本。
- 增加持久化缓存和调用账本；修复并发写账本、SDK 客户端和缓存临时文件的线程安全问题。
- 缓存回放会重新校验响应；损坏或不兼容缓存不会直接成为正式制品。
- 增加结构化响应校验、截断响应处理、修复提示词，以及正式 / INVALID / 历史轮次归档。
- `--chapters`、`--drop`、`--migrate`、`--revalidate`、角色清理等维护路径可以实际用于局部恢复。
- 统一锚点规范化和人物引用恢复，减少标点、引号及别名造成的假失败。

### 4.2 Stage 3–5

- Stage 3 `--check-only` 能读取 `.INVALID` 候选，失败后不再只能整阶段重跑。
- Stage 5 加入长度超限重试、低推理裁剪、裁剪安全回退、逐章失败隔离和定向刷新。
- 修复 `】` 未被视为终止标点的问题。
- 修复基线告警把同一章的多个 finding 重复计数的问题；第三本现在正确显示 15/15 章，而不是 20/15。
- 只有通过校验的章节才晋升正式制品；失败候选保留在轮次目录，便于恢复和审计。

### 4.3 Stage 6–7

- 数字事实检查同时比较规范化后的“数值 + 单位”，并过滤普通动词“成”造成的假数字单位。
- Stage 7 在付费改名前先做恒等预检；缺制品时返回安全报告，不再先花费请求。
- 修复常见姓氏被误判为亲属组、缺失 / 重复 / 孤儿映射未充分检查的问题。
- 修复“女主方衡→女主沈凌”一类复合标签被误判成亲属称谓变化；“姐姐→妹妹”仍会被正确阻断。
- `--revalidate` 现在根据当前制品重建确定性 finding，不再回放旧报告中的陈旧结果。
- `--apply-edit` 可从首个 `.INVALID` 候选继续，并对编辑文件路径给出明确错误。
- 修复 Stage 7 正文陈旧性检查分母错误，现按实际 8 / 19 / 15 章扫描。

### 4.4 CLI、契约与回归

- 将运行参数校验放到昂贵上下文和 LLM 调用之前；不支持的参数不再被误导成“加 `--yes` 即可”。
- 明确 `--apply-edit` 的路径参数属于公开 CLI 契约。
- 修复层次约束测试发现的裸 `json.loads`：Stage 2 范围违规行改为类型化 Pydantic 模型解析。
- 为上述恢复路径、错误边界、计数口径和误报场景补充了回归测试。

## 5. 仍需优化的方向

### P0：建议优先处理

1. **Stage 2 上下文与 token 规模**

   当前逐章请求会携带过大的全书上下文，长书近似形成 O(章节数 × 全书长度) 的输入增长。建议采用“稳定全局 grounding + 当前章全文 + 有界相邻窗口 + 滚动连续性状态”，同时利用供应商前缀缓存。这里会影响保真和秘密时间线，属于需要先确认的契约调整，不能只为省 token 粗暴截断。

2. **材料锚点 schema**

   `material_malformed` 命中了 41/42 个成稿章节（8/8、19/19、14/15），说明 `starts_with` / `ends_with` 的自由文本边界系统性携带标点或引号残片。建议把锚点改为：原文精确 `text`、源字符 `start/end`、规范化文本及恢复方式；晋升正式蓝图前必须验证 offset 和文本一致。需要提供旧制品迁移。

3. **语义级秘密 / 文案校验**

   当前 secret 与 hook 主要靠字面探针。第一本多个秘密连揭示章自身都命不中，Stage 6 的候选也可能字面全绿但语义上提前说出结果。建议增加一次书级语义审判：先从文案和章节抽取结构化 claim，再把 claim 对齐到 `reveal_chapter`；无法确认时必须是 UNVER，不能当 PASS。

4. **可观测性与 provenance**

   当前新鲜制品仍常显示 `unknown(consumed_unresolved/undeclared)`，Stage 5 长时运行也缺少可靠心跳。建议建立按节点注册的 consumed projection，统一 freshness 计算；账本增加 attempt、finish reason、timeout / retry 分类、latency、退避时间和章节进度。先补这层，后续 prompt 实验才有可信对照。

### P1：质量与吞吐

5. **Stage 5 调度**：在供应商限流下做有界并发和加权调度，保留逐章提交；重试加入指数退避与抖动。优先重写篇幅、事件完整性真正异常的章，裁剪只作为最后手段。
6. **Stage 3 prompt**：明确禁止人物名、专有名词和剧情机制进入风格字段，并加入“系统 → 信息提示音 / 任务界面”这类正反例；更稳妥的做法是先脱敏实体再抽风格。
7. **Stage 4 plan**：三本均从 95/159/160 个源节拍压到 70/110/110 个计划节拍，仍出现 dense / flat INFO。可先用确定性分组器满足预算和分布，再让 LLM 只做叙事取舍。
8. **对话与篇幅控制**：prompt 应下发逐章源对话比例和目标带，而不只给全书均值；对明显章节离群做定向重写，不要用全书 0.98× 掩盖单章偏差。
9. **改名不变量**：第二本人工检查发现“阿九→阿七”改变了数字 / 排序语义，后改为“玄九”。建议对别名里的数字、辈分、排行、官阶建立确定性保持规则。
10. **残留扫描**：继续保留 high / low 分级，但增加实体上下文和词法边界打分，减少“投桃报李”等普通词误报；姓氏家族别名应尽量在 Stage 2 结构化收齐。

### P2：校验口径与维护

11. `invented_number` 在部分样本中源文本基线比成稿更差，需区分事实数字、固定说法、概率表达和成语。
12. 机械归一化统计目前没有完整汇总到全书 review；应聚合 `punct_fixed / quotes_fixed / paras_fixed`，或明确标为不适用。
13. 首次确定性修正目前常要求显式 `--migrate`；可考虑在不改变语义时自动修正并留下审计记录。
14. 全量测试仅剩 Starlette / httpx 的弃用警告，应通过兼容版本升级或 pin 消除，避免将来升级变成故障。

## 6. 建议的实施顺序（待讨论）

我建议分三批：

1. 先做 provenance、进度心跳和逐请求 latency / retry 账本。这一批语义风险最低，会让后面的效果和成本可测量。
2. 再一起设计 Stage 2 锚点 schema 与上下文架构。这会改制品契约和模型可见信息，建议在写代码前确认“保真优先”边界和迁移策略。
3. 最后做书级语义审判、Stage 3/5 prompt 实验和改名语义不变量；用同三本样本作为固定回归集，对比质量、耗时和 token。
