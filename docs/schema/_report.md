# 校验报告（`CheckReport`）

**载体已定：Pydantic v2**——但本文只定**内容**，模型照它写，**方向别搞反**。
所以下表里不出现任何 Python 类型标注，只出现「类型 / 必填 / 取值面 / 证据」。
证据列的取值见 `docs/schema/_README.md`；本文大量使用 stage0 那个 **`设计`**
——**新形状盘上零样本**，还没有任何东西验证过它。

## 为什么它单独一份，而不是 `_common.md` 的第十节

`_common.md` 管的是**每份产物里都有的那几个键**（`_provenance` / `Finding` / `usage`）。
本文管的是**产物之外的一份东西**：校验报告不落在任何一份 artifact 里，它是
`--check-only` 打印的、`/api/check/<node>` 返回的、inbox 列出来的那一份。
两者的消费方、生命周期、改版节奏都不一样，合成一节会让「产物契约」与「API 契约」共用一个版本号。

⇒ `docs/schema/_report.md` ↔ `contracts/schema/report.py`，文件名一一对应（同 `_common.md` ↔ `common.py`）。

## 它要消灭的那三种已发生的故障

| # | 故障 | 实测证据 |
|---|---|---|
| ① | **「跑过没命中」与「根本没跑」在报告上同形** | stage7 的 `rn_unregistered` 在判据表里注册着、**全仓 0 行实现**，而它是 `info` ⇒ **每本每次都打绿灯**（`stage7.md` 事实⑥） |
| ② | **度量与告警合流** | `check_stage5_review.json` 的 `info` 桶有 **59** 条，其中 **41 条**是 `〔度量〕`——`SEVERITY` 四级在载体上只剩三级，靠**措辞前缀**区分（`invariants.py` 已记着这条：61 条结论里 41 条是 metric，画成警告色整屏都是红黄） |
| ③ | **记账记了没有出口** | stage2 的 8 个记账键有 **5 个 0 出口**、stage3 的 3 个**一个都没有**（`stage3.md` §五） |

> ### ⚠ 旧形状长什么样，以及它为什么救不回来
>
> 盘上两份真实抓包（`docs/design_brief/05_samples/check_stage2.json` ·
> `check_stage5_review.json`）的顶层十个键：
> `title` · `sid` · **`oks: str[]`** · `unver[]` · `info[]` · `hard[]` ·
> `passed` · `hard_count` · `unver_count` · `badge`。
>
> **`oks` 是一串散文字符串**（`"顺序：与章序一致"` / `"判的是 review_4（8 份成稿）"`），
> **没有 rule id**。⇒ 一条判据「跑了没命中」与「压根没被调用」在响应里
> **不是难以区分，是无法区分**——前者进 `oks`，后者哪个桶都不进，而客户端看不见桶以外的东西。
> 补一个 `skipped` 桶也救不了：桶是由**产出**填的，没跑的那条判据本来就没有产出。
>
> ⇒ **权威必须从「结论的集合」翻转成「判据的集合」。** 这是本文档全部内容的那一句话。

## 一、`STATUS` —— 判据行的四态

一条**注册判据**在一次校验里的处境。取值面的唯一落点是 `contracts/invariants.py::STATUS`。

| 取值 | 意思 | 与它最容易混的那个 |
|---|---|---|
| `ok` | 跑了，没命中 | 与 `skipped` 混 ⇒ 故障① |
| `hit` | 跑了，命中了，`findings[]` 非空 | — |
| `unver` | 跑了，但**这次没有判别力样本**（没有名表 / 名表过滤后为空 / 盲区 100%） | 与 `ok` 混 ⇒ 打一盏「保证会亮的绿灯」 |
| `skipped` | **注册了，而实现这次没有被调用** | 与 `ok` 混 ⇒ 故障① |

⚠ **`unver` 不是「出错了」，`skipped` 才是。** 前者是判据诚实地说「这次我够不着」
（判据的边界，不进待办清单——`INBOX_KIND` 的注释已写死这条）；
后者是**系统自己的漏洞**：一条注册在案的判据，这一次没有任何代码去执行它。

⚠ **`skipped` 必须携带原因**（`why`）。「没被调用」有两种：实现根本不存在、
或实现存在但这条路径没走到（`--check-only` 不跑落盘期闸门）。分不开就没法判断该不该修。

## 二、`RuleLine` —— 一条注册判据，恰好一行

| 字段 | 类型 | 必填 | 内容 | 证据 |
|---|---|---|---|---|
| `rule` | `str` | **是** | 判据表的 key。**与 `wontfix.json` 的键、`_provenance.fixes` 的引用是同一个字符串** | **契·码** |
| `sev` | `str` | **是** | `hard｜info｜metric｜unver`。**从注册表取，不由产出决定** | **契·码** |
| `status` | `str` | **是** | §一那四个 | **设计** |
| `item` | `str` | **是** | 人读的一句话「这条在守什么」。**从注册表取** | **契·码** |
| `requirement` | `str` | **是** | `R-x.y`。让报告能反查「这条判据在满足哪条需求」 | **契·码** |
| `check_kind` | `str` | **是** | `mechanical｜semantic`：是确定性检查还是 LLM 语义审判。**与严重度正交** | **契·码** |
| `remediation` | `str` | **是** | `llm｜human｜deterministic｜none`：工作流的下一步，从现有 `repair/fix/sev` 统一投影 | **契·码** |
| `fix` | `obj｜null` | **是** | 可执行修复路由 `{node, flags[], paid}`；无结构化路由时为 `null` | **契·码** |
| `findings` | `Finding[]` | **是** | 这条判据这一次的产出。**度量的读数也装在这里** | **设计** |
| `why` | `str｜null` | **是**（可为 `null`） | `status='skipped'｜'unver'` 时非空，其余为 `null` | **设计** |
| `baseline` | `str｜null` | **是**（可为 `null`） | 词表类判据的基线命中率。`wordlist=True` 时**必填** | **契·码** |

**五条后置条件**（载体在守，不是判据）：

1. `sev == 'metric'` ⇒ `status != 'hit'` —— **度量永远不「命中」**。
   它是无条件产出的读数，`hit` 这一态对它没有意义（`invariants.WHO_CHECKS` 的 `METRIC` 那条已写死）。
2. `sev != 'metric'` 时：`findings` 非空 ⇔ `status == 'hit'`。
   **度量不在此列**——它有读数但不命中，这正是上一条的另一面。
3. `status == 'skipped'` ⇒ `findings` 为空（这一次一条代码都没执行过）。
4. `status ∈ {skipped, unver}` ⇔ `why` 非空。跑过的两态**不许**带 `why`（那是噪声）。
**外加一条不由 `RuleLine` 自己守的**（它身上没有 `wordlist` 这个字段）：

5. `wordlist=True` ⇒ `baseline` 非空 —— **`Q-9`：永远打印基线**。
   没有基线命中率的词表判据「等于不知道自己在说什么」。
   ⚠ **这一条由两段合起来保证**：注册期 `contracts/rules.py::_validate` ⑤ 拦住
   「词表判据没填基线」，构造期 `builder` 无条件把 `rule.baseline` 原样带出来（不重算、不省略）。
   ⇒ 报告这一侧漏不掉。配一条测试从两头夹住这条链。

### 2.1 严重度、检查性质与处置路由是三个正交轴

- `sev` 回答“影响有多大”；语义泄底可以是 HARD，语义覆盖不足可以是 INFO/UNVER。
- `check_kind` 回答“这个结论怎么来的”。Stage 0–4、7 现役判据全是 `mechanical`；Stage 5 与 Stage 6 各有独立的 `semantic` 伙伴审判（注册表守卫钉着：语义判据只许出现在这两层）。
- `remediation` 回答“下一步谁能修”。`REPAIR_UNIQUE` 或已注册的付费 fix 是 `llm`；0 成本结构化 fix 是 `deterministic`；无安全自动路由是 `human`；metric 是 `none`。四类各自的修复路由与成本上界见 `docs/REPAIR.md`。

这个投影故意**不把 `REPAIR_FREE` 标成 LLM 自动修复**。它表示理论上可重写，但满足路径不唯一；当前 Stage 5 付费自救明确拒绝它，因为模型可能通过删内容或编内容“修绿”。

> #### ⚠ 为什么度量的读数**不另开一个 `readings` 字段**
>
> 那会让同一件事有两个落点，而 `Finding` 已经是全链唯一那一份
> （原型有 5 份拷贝、3 种字段签名，`_common.md` §七 开头就记着这条）。
> **区别不在字段上，在 `status` 上**：结论类判据「有产出」就是「命中」，
> 度量「有产出」是它的常态。⇒ 一个字段 `findings`，两条按 `sev` 分开的后置条件。

⚠ **`findings` 里的 `Finding` 只能经工厂构造**（`_common.md` §七 设计要点 1）：
`sev` / `item` / `owner` / `actionable` 一律从注册表取，调用方只给 `detail` + `evidence`。
⇒ 一条 finding 不可能与它所属的那一行说的不一致——**它们读的是同一个 `Rule` 对象**。

### 2.2 ⚠ `actionable` 从 `repair` 派生，**不给 `Rule` 加第二个字段**

`_common.md` §七 要求工厂从注册表取 `actionable`，而 `contracts/rules.py::Rule` 上**没有这个字段**，
只有 `repair`（`UNIQUE｜FREE｜NONE`）。两者的不变量正好同构：

- `rules.py::_validate` ③：`repair != 'NONE'` ⇒ `owner == 'stage5'`
- `common.py::Finding._postconditions` ③：`actionable` ⇒ `owner == 'stage5'`

⇒ **`actionable := (repair != 'NONE')`**。加一个字段等于给同一件事开第二个落点，
而「同一件事的第 N 个落点必然分家」是本项目要消灭的那条病。

> #### ⚠ 裁决（2026-08-11，移植 stage6 时）：**两条不变量一格都不放宽**
>
> 悬着的问题是：stage6 / stage7 的契约文档写着本层 `actionable=True`
> （`stage6.md` §四 12 条 · `stage7.md` §六 16 条），而那两层的 `actionable`
> 意思是「**人能 0 成本改掉它**」（`--pick` 换一条候选 / `--apply-edit` 改一个字），
> 不是「写作层能修」，`owner` 全是它们自己那一层。
>
> **裁决：那两层全表 `repair='NONE'` ⇒ `actionable` 全 `False`。** 四条理由：
>
> 1. `repair` 回答的是「**进不进付费自救**」，而本层的答案就是**一条都不开**
>    （2026-08-08 已裁：已经有更便宜的路）。`repair='NONE'` 是**字面正确**的，不是妥协。
> 2. `actionable` 今天的定义是「写作层能修」，stage6 一条都不是。
>    硬把第二种意思塞进同一个名字，就是判据 32 那条：**名字先于证据定下来，
>    后来读报告的人会按名字去解释它**——前端拿到同一个布尔值却要按层解释。
> 3. 原型的 `REPAIR_FREE7` **零真实消费方**（只喂了一句 `assert_repair_admission`）。
>    给一个没有消费方的语义抢一个字段名，与 `PARTIAL_MASK_FIELDS` 被拦下来是同一条理由。
> 4. **语料已经替它投过票**：`tests/corpus.py::_migrate_findings` 写着
>    `setdefault('actionable', False)`，而盘上 6 份 stage6 产物在这个前提下 `model_validate` 全过。
>
> ⇒ 「人能 0 成本改掉」写进 `Rule.note`（那 12 条各一句），
> **不进载体**。stage7 移植时按同一条办，届时若发现真有消费方需要它，
> 那是一次**独立的**契约改版，该被单独看见。

## 三、`CheckReport` —— 顶层

| 字段 | 类型 | 必填 | 内容 | 证据 |
|---|---|---|---|---|
| `sid` / `node` / `stage` | `str` | **是** | 判的是谁。⚠ `node` 是 `<stage>.<动词>`，`n1..n9` 整套已退役 | **契·码** |
| `provenance` | `obj` | **是** | §五。**空也要报** | **设计** |
| `rules` | `RuleLine[]` | **是** | ⭐ **权威**。每条注册判据恰好一行 | **设计** |
| `accounting` | `obj[]` | **是** | §六。**空也要报** | **设计** |
| `badge` | `str` | **是** | `pass｜amber｜fail`。**服务端算**（`R-11.7`） | **三源** |
| `passed` | `bool` | **是** | 服务端算 | **盘·码** |
| `counts` | `{状态: 个数}` | **是** | 服务端算。四个状态各一个数 | **设计** |

### 3.1 ⚠ 四个 sev 桶**不再由服务端发**

`oks` / `unver` / `info` / `hard` 四个数组**从响应里消失**。前端要分桶就拿 `rules[]`
按 `sev` groupby——**同一份数据只有一个落点**。

理由不是「少发几个字段」，是**桶这个形状本身携带不了 `skipped`**（见开头那个框）。
留一份派生的桶当兼容层，等于把已经翻转过来的权威又翻回去一半，
而两个落点必然分家——`hard_count` 与 `hard[]` 的长度已经是两个字段了。

⚠ **代价要说清**：`web/src/types/stages.ts` 的 `CheckReport` interface、
两份 mock、`check/CheckPanel.tsx`、`screens/inbox/InboxScreen.tsx` 都要跟着改。
用户已裁决**骨架阶段当 `web/` 不存在**，这笔账记在 Phase E（接 `/api/enums` 时一起处理）。

### 3.2 `badge` / `passed` / `counts` 只在服务端算

`R-11.7`：**贵贱、通过与否只有一处算**。前端拿到 `rules[]` 之后完全有能力自己数一遍，
而那一刻就有了第二个答案——两个答案必然分家，且分家时**没有任何东西会报错**。

## 四、徽章 —— 一个函数，三态

```
HARD 且 status ∈ {hit, skipped}          ⇒ fail
否则 有任何 status ∈ {unver, skipped}    ⇒ amber
否则                                      ⇒ pass
```

**⚠ `skipped` 进 `fail` 那一支（当它挂在 HARD 上），不是 amber。**
一条阻断级判据这次没被执行，与它执行了并且命中，对调用方是同一件事：
**你不能拿这份产物往下走**。把它降成 amber 等于说「大概没事」，而我们恰恰不知道。

**⚠ `amber` 不是绿色**（`invariants.BADGE` 已写死）：`passed and unver_count > 0`。
⇒ **「pass + N 项未验证」在类型上不可能**——它要么是 `amber`，要么那 N 项不存在。

⚠ `sev='metric'` 的行**永不影响徽章**。度量无条件产出、永不命中，
让它参与判定就是把「现状读数」重新并回「告警」那一支（判据 21）。

## 五、`provenance` —— 报告的第一节，**来源在前，判定在后**

`Q-4` 的形式要求：**对不上时报出来的一堆违规是「拿新尺子量旧布」**，
不说破就会被当成一次回归。⇒ 第一节恒是来源，**空也要报**（`R-5.10` 就是补这一行的）。

| 字段 | 类型 | 必填 | 内容 |
|---|---|---|---|
| `freshness` | `str` | **是** | `fresh｜stale｜unknown`。算法唯一落点 `novel/prov.py::freshness` |
| `reason` | `str` | **是** | `FRESHNESS_REASON` 之一。**用 id 不用措辞** |
| `ghosts` | `str[]` | **是** | ⭐ **点名**报出指向已删文件的边。**空也要报** |
| `edges` | `obj[]` | **是** | 逐条边：`key` / `state` / `reason` / 记的指纹 / 现在的指纹 |
| `invalid` | `bool` | **是** | 判的这一份是不是 `.INVALID` 稿 |
| `revalidated` | `bool｜null` | **是**（可为 `null`） | 三态照 `_provenance` 原样带下来。`null` = 键不在 |
| `origin` | `str｜null` | **是**（可为 `null`） | 同上。`human` = 人工稿 |

> ### ⚠ 幽灵边必须点名 —— `Q-4` 亲自点过的一个 bug
>
> 原型的比对函数对「取不到指纹」的条目**静默跳过**。盘上真有一条：
> `成年人不做选择` 那本的 `stage4/writer_context.json` 挂着一份 `.INVALID` 的计划，
> 而那个文件已经不在了（0 成本提升路读完问题稿就把它删了）。
> ⇒ 取不到指纹 = 那份上游已经不在盘上，**要报出来，并按名字说是哪一条**。

⚠ **`.INVALID` / `revalidated` / `origin` 进第一节，是本文档立的一条新要求。**
`_common.md` §五只定义了这三个键，没说它们要进报告。登记在这里，别当成早就有的。
理由与幽灵边同源：这三个键回答的是「**你现在看的这一份是怎么来的**」,
而它们今天在 stage3 的报告里**一行都没有**（`stage3.md` §五）。

## 六、`accounting` —— 记账键的出口，一张**会炸**的表

`_common.md` §九 的三条形式要求（空也要报 · 一行常驻非空才展开 · 出口在报告不在 stdout）
在这里变成唯一落点：**每层声明自己有哪些记账键**（`novel/report/accounting.py::ACCOUNTING`）。

| 情况 | 处置 | 它防的那次损失 |
|---|---|---|
| 产地记了某个键，声明表里**没有** | **抛 `AccountingKeyUnregistered`** | stage2 的 8 个记账键有 5 个 0 出口、stage3 的 3 个一个都没有 |
| 声明表里有、产地**没记** | 打 `[????] 未记录` | 「记了 0 次」与「压根没记」必须分开 |
| 值为**空** | 打 `… 0 处` | 「没改过」与「没在报」必须分开 |

一行的形状：

| 字段 | 类型 | 必填 | 内容 |
|---|---|---|---|
| `key` | `str` | **是** | 记账键名 |
| `item` | `str` | **是** | 人读的一句话「这个数在数什么」 |
| `recorded` | `bool` | **是** | 产地这次记了没有。`False` ⇒ 渲染成 `[????] 未记录` |
| `count` | `int` | **是** | 值为空时是 `0`，渲染成 `… 0 处` |
| `detail` | `str[]` | **是** | 非空才展开的那部分。**空也要有这个键** |

> #### ⚠ 它归 `RefusedByStructure` 那一族，不归 `TerminalState`
>
> `_common.md` §九 那张表写的是「**显式终态**」，而那是**口语义**（＝别静默）。
> 按 `novel/errors.py` 自己的分界线——**「谁的错」**——记账（`ctx.account(...)`）
> 与声明表（`ACCOUNTING`）是**同一批代码**的两处，对不上就是代码自相矛盾，
> 不是数据说走不下去了。⇒ **是 bug，栈要留全。**
>
> 这一处**细化**登记在这里，而不是去改 `_common.md`：那一份定的是「必须炸」，
> 本文定的是「炸成哪一族」。两份没有冲突，只有粒度差别。

⚠ **为什么「表里没有」是终态而不是一行警告。** 另外两种情况都是**报告变差**
（少一行、或多一行没用的），而这一种是**产地在记一笔谁也读不到的账**——
它已经写进了 `_provenance`，人却永远看不见。原型正是这个下场：13 个记账键，6 个 0 出口。
⇒ 加一个记账键的成本必须是「同时给它一个出口」，否则加不进去。

## 七、已经查清楚、结论就是「查不了」的

登记在这里免得被当成漏项。

1. **报告证明不了「实现是对的」，只能证明「实现被调用过」。**
   `skipped` 抓的是「注册了没人调」，抓不到「调了但判错了」。
   后者只能靠 `tests/` 里那条「每新加一条 HARD 判据，就要有一份会让它红的样本」。
2. **`counts` 不是跨书可比的。** 一条判据的分母随书变（stage6 的分母只有 9 或 3），
   两本书的 `hit` 数放在一起比没有意义。要横向比必须先说出分母，而分母不在本结构里。
3. **`accounting.count` 只数「记了几笔」，不数「改对了没有」。**
   落盘前的确定性改写是否正确，判据 24 要求断言**计数**而不是断言字段值——
   那条判据在判据表里，不在这张出口表里。
4. **报告不在逐字节验收范围内。** 所以一切机器要读的东西都是 **id 不是措辞**
   （`status` / `reason` / `rule`）。拿字符串前缀认原因会随一次措辞改动静默断掉——
   旧形状的 `〔度量〕` 前缀就是这个下场。
